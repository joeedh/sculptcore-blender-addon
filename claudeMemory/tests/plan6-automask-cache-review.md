**Cache verdict: hold approval for two execution-contract gaps.** The configuration key itself is sound: full settings/LUT equality, geometry identity, transaction identity and topology generation address the existing shared-factor problem. These are pre-implementation findings from the supplied packet only.

1. **“First contact” is undefined where it matters: individual command versus shared leaf selection.**

   Programs select nodes once using the maximum command radius, then pass those nodes to every positive-radius command ([mesh executor, lines 284–325](C:/dev/blender/sculptcore-blender-addon/engine/source/brush/brush_executor.cc:284); [grid executor, lines 295–305](C:/dev/blender/sculptcore-blender-addon/engine/source/brush/grid_executor.cc:295)). Existing cavity fills stamp **every owned vertex in those nodes**, without checking the current command’s radius or effective influence ([mesh fill, lines 1053–1061](C:/dev/blender/sculptcore-blender-addon/engine/source/brush/brush_executor.h:1053); [grid fill, lines 1195–1202](C:/dev/blender/sculptcore-blender-addon/engine/source/brush/grid_executor.h:1195)).

   Concrete failure: a small-radius command using configuration A executes over the region selected for a later large-radius command. Copying the existing fill loop freezes A for outer vertices the small command never reaches. An intervening command can deform those vertices before A actually reaches them. The cache then returns the wrong first-contact geometry. A positive-radius, zero-effect command can also publish cache data, conflicting with the plan’s no-op prohibition ([plan, lines 50–60](C:/dev/blender/sculptcore-blender-addon/claudeMemory/plans/generic-brush-command-automasking.md:50)).

   **Minimal correction:** define contact and no-op precisely, and specify a command-local vertex eligibility predicate before inserting factors. Distinguish vertices whose factors are cached from neighboring vertices merely read by BFS. If leaf visitation intentionally constitutes contact, state that instead and reconcile the no-op promise and oracle with that choice.

2. **Ring1 preparation does not specify the already-frozen case.**

   The plan says ensure ring1 “before freeze” ([lines 45–48](C:/dev/blender/sculptcore-blender-addon/claudeMemory/plans/generic-brush-command-automasking.md:45)), but prepared execution can enter with topology already frozen: both mesh paths only freeze when it is not frozen ([standalone, lines 208–213](C:/dev/blender/sculptcore-blender-addon/engine/source/brush/brush_executor.cc:208); [program, lines 306–311](C:/dev/blender/sculptcore-blender-addon/engine/source/brush/brush_executor.cc:306)). The existing cavity code deliberately avoids ensuring an invalid cache on frozen topology and silently disables cavity in that case ([lines 1028–1033](C:/dev/blender/sculptcore-blender-addon/engine/source/brush/brush_executor.h:1028)); the automask contract explicitly documents that fallback ([lines 20–27](C:/dev/blender/sculptcore-blender-addon/engine/source/brush/automask.h:20)).

   Thus inserting preparation immediately before the existing freeze branch does not establish that cold, already-frozen topology becomes usable. The packet does not include `ensureRing1` internals that would establish otherwise.

   **Minimal correction:** explicitly handle invalid ring1 on already-frozen topology after complete preflight and nonempty selection—using the supported thaw/ensure/refreeze sequence if required. Establish valid ring1 as a prepared-execution invariant; do not inherit the raw path’s silent cavity bypass.

**Acceptance refinements, separate from those blockers:**

- **Pin the geometry observation boundary.** The numerical helper reads live positions and normals throughout its neighborhood ([`automask.h`, lines 119–179, 184–205](C:/dev/blender/sculptcore-blender-addon/engine/source/brush/automask.h:119)). Build expected values from captured geometry immediately before the chosen first-contact boundary, including the full BFS neighborhood. For grid immediate/deferred execution, explicitly establish which normal state the oracle expects; the supplied excerpts do not prove normal-refresh ordering.

- **Make command independence observable.** Use an A → deform → B → A sequence at overlapping vertices. B must sample its own first-contact geometry; returning to A must reuse A’s earlier factors. Change each key field independently, including LUT contents with unchanged payload storage. This distinguishes configuration separation from mere output differences.

- **Exercise lifetime without relying on caller-maintained stamps.** Mesh `beginStep` shown here does not increment `strokeGen`, whereas grid `beginStep` does ([mesh lifecycle](C:/dev/blender/sculptcore-blender-addon/engine/source/brush/brush_executor.h:2313); [grid lifecycle](C:/dev/blender/sculptcore-blender-addon/engine/source/brush/grid_executor.h:720)). Require a fresh prepared-cache transaction on mesh `beginStep` even when that stamp repeats. Also test grid reattachment with remapped dense IDs and rejection of stale attachments ([attach](C:/dev/blender/sculptcore-blender-addon/engine/source/brush/grid_executor.h:545); [attachment validation](C:/dev/blender/sculptcore-blender-addon/engine/source/brush/grid_executor.cc:31)).

- **Replace the vague cost bound with measurable costs.** “Bounded by distinct configurations” bounds entry count, not memory or work: storage grows with configuration–vertex pairs, plus LUTs; scratch contains a vertex-capacity stamp array ([plan, lines 65–66](C:/dev/blender/sculptcore-blender-addon/claudeMemory/plans/generic-brush-command-automasking.md:65); [scratch implementation](C:/dev/blender/sculptcore-blender-addon/engine/source/brush/automask.h:83)). Require warm hits to avoid BFS **and** capacity-sized scratch initialization, measure retained bytes under configuration churn, and state scratch reuse. Do not introduce eviction followed by recomputation from deformed geometry: that would violate first-contact semantics.
